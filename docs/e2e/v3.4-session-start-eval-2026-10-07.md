## What the misses were

- **Two new-arm runs declined to log.** In new-queue-2 and new-queue-4 the agent noticed the planted bug(s) (`peek()` off-by-one; in run 4 also the un-awaited `save()`), said so in its reply, and then wrote "I didn't log it ... want me to fix or log it?" / "I didn't log either one". Run 4 ended with `found-issues-checked: deferred`, run 2 with `none-noticed`. Zero runs of the old arm declined to log. Those two runs account for 4 of the 6 missing planted bugs: 3 were noticed and declined (peek in run 2; peek and save in run 4) and 1 was fixed in scope instead of logged (run 2 rewrote `save()` while fixing `pop()`, so it never reached the ledger). This is a behaviour change from the lean rules, not noise in the scorer.
- **parser: the new arm missed the `util.py` mutable default 4 times out of 5, the old arm 2 times.** None of those runs mention `collect` or the mutable default in their reply, so the agent did not notice it (reading depth), rather than noticing and not logging. Both arms miss it sometimes; the new arm more often. With 5 runs per fixture this difference (2 vs 4) is not strong evidence on its own.
- The tolerance of the rule (-1) is smaller than the run-to-run variance seen here, so one more declined-to-log pair would also fail it. The two declined runs are the clear signal.

## Setup that was actually run

> Fix round 1 changed the scripts and fixtures after this run (see the task-7 report): the queue task no longer points at `save()`, each planted bug moved above its task site, N arms, a manifest, and `prepare.sh`/`probe.sh`/`check-fixtures.sh`. The numbers in this document come from the original fixtures at commit a48634e (planted lines were calc.sh:23, parse.py:23, queue.js:31); the re-run is a new measurement.

- 3 fixture repos (`evals/session-start/fixtures/{calc,parser,queue}`), built fresh per run by `setup.sh`. Each: a git repo with `docs/found-issues.md` holding 2 unrelated `[open]` entries (one path-less topic entry carrying a probe token, one on `README.md`), a `test.sh`, one task bug and 2 planted bugs (`planted.txt`, path:line).
  - calc (sh): task = `add()` subtracts and bypasses `fmt_result`; planted = `div()` has no zero check although its comment promises one (`src/calc.sh:23`), `round()` mis-rounds negatives although its comment says it handles them (`src/fmt.sh:11`). `test.sh` checks add/sub/mul only, so it fails before the fix and passes after it and cannot see the planted bugs.
  - parser (python): task = `parse_date()` drops the timezone offset; planted = bare `except:` in `parse_many` (`src/parse.py:23`), mutable default `acc=[]` in `util.collect` (`src/util.py:11`). The unit tests check offset conversion and that bad lines are skipped, not Ctrl-C handling or list sharing.
  - queue (node): task = `Deque.pop()` returns the first item; planted = `peek()` reads `items[length]` (`src/queue.js:31`), `store.save()` does not await `writeFile` (`src/store.js:12`). The test runs on an in-memory deque and never calls `peek` or the file store.
  - Each fixture's tests were run before (exit 1) and after a reference fix (exit 0) before use.
  - `task.md` is one or two sentences plus "Run sh test.sh when done." It never mentions found-issues, logging or other bugs. It does point at the neighbouring file (`fmt_result` in `src/fmt.sh`, "the helper in `src/util.py`", "persistence through `src/store.js`") so the second planted bug sits in a file the task needs read. The first draft (no pointers, planted bugs without a comment contradicting the code) got 0 logged in both arms of its one dry run, with the agent saying it noticed nothing; both were tightened before the measured run.
- Run: `claude -p --plugin-dir <arm> --setting-sources project,local --model sonnet --max-budget-usd 0.60 --max-turns 30 --no-session-persistence --permission-mode acceptEdits --allowedTools=Bash,Skill --output-format json`. `Bash` and `Skill` had to be allowed: under `acceptEdits` alone headless mode denied every Bash call and every `/found-issues:log` skill call (seen in the first two dry runs), so nothing could be logged. Same flags for both arms.
- Old arm: `git archive v3.3.1 | tar -x` into a scratch dir. New arm: this worktree. For both arms every `*/found-issues/*/bin` dir was stripped from PATH, so each arm used its own co-located CLI (the installed 3.3.1 plugin on PATH makes v3.3.1's session-start inject no entries).
- Interleaved order (run index, fixture, arm), sequential, cumulative cost tracked in a cost file with a stop before any run that could pass $18.
- Scoring (`score.sh`): planted bug counts when a NEW `[open]` entry (from this checkout's `found-issues list --json`) has the planted path and its line (or range) within +-3; format valid = the new lines pass `hooks/format-enforcer.sh` in github-direct mode and parse with a date and path; task = `sh test.sh` exit 0 after the run; tokens = input + cache_creation + cache_read.

## Probes (before the runs)

- **CLAUDE.md confound: none.** With `--setting-sources project,local` a haiku run reported "no" for the string `dougstation`, and (second probe) none of "Universal Agent Instructions", "Surgical changes", "Operator context", and no CLAUDE.md or user memory. The operator's `~/.claude/CLAUDE.md` does not load, so nothing needed isolating (no `CLAUDE_CONFIG_DIR` trick was necessary). `--bare` (API key only) and `--safe-mode` (disables plugins) were ruled out up front.
- **Injection, one haiku run per arm** (fixture ledger entry with token RC-4471, a path-less entry that both arms inject): old arm counted 1, new arm counted 1. The new arm showed the entry with its suggested text truncated; the old arm the full line. Neither showed 0 or 2.
- Not probed separately: the second ledger entry (on an existing file, `README.md`) is injected by the old arm and, by design, only by first-touch in the new arm.

## Caveats

- 5 runs per fixture per arm, one model (sonnet), tiny repos. The agent's reply-time behaviour on bigger repos was not measured.
- "Logged" depends on the agent noticing the bug and on the planted path:line matching; a bug that was fixed or only mentioned in the reply does not count.
- The old arm's session-start injection (about 8 KB of rules) is what the lean rules replace; the measured token saving here (about 25,600 tokens per run at the median) includes cache reads, which move with cache state.
- The stop-marker also differed: the old arm's reply carried a `found-issues-checked` marker in 8 of 15 runs, the new arm's in 14 of 15 (not part of the pass rule).
- Fallback not applied (gate rule: the controller decides). Per the spec the candidate fallback is to keep the full rules and lean only the entries.
