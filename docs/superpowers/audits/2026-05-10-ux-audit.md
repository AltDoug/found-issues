# found-issues — end-to-end UX audit

**Date:** 2026-05-10
**Audit context:** Fresh-eyes review of v1.0.5 (post-defer-recurrence-flow + statusline self-heal). Conducted by a session that did *not* ship today's PRs.
**Scope:** 10 surfaces a new user touches in their first 30 minutes. See `/Users/diogosilvasena/Documents/found-issues-ux-audit-handoff-2026-05-10.md` for the handoff brief.
**Method:** Walked each surface against the shipped artifacts (README, `commands/*.md`, `bin/found-issues`, `hooks/*.sh`, `lib/*.sh`, `AGENTS.md`, `skills/rules/SKILL.md`, dogfood `docs/found-issues.md`). No CLI execution — pure document/code review with the imagined-user lens. Where a friction is observable from the code alone (e.g. divergent docs, hard-block equality checks), it's flagged with a confidence note.

Priority ladder used throughout:

- **P0** — silent breakage, data loss, or a workflow that hard-blocks valid work. Ship in v1.0.6.
- **P1** — friction that costs a new user > 1 min on the golden path, or causes them to mentally model the system incorrectly. Ship in v1.0.6 or fast-follow.
- **P2** — friction that's annoying but recoverable. Batch into v1.1 or next themed release.
- **nice-to-have** — polish; revisit if a second user hits it.

The plugin is in good shape. Day-to-day mechanics work, the closure loop is sturdy, and v1.0.3–v1.0.5 self-heal the historical breakage patterns. The new-user golden path (install → setup → see counter → log → see entry close) is intelligible.

## Surface 1 — First install + setup flow

### Walked-through experience

1. New user lands on the GitHub README. Reads the tagline (*"Your AI agent has a blind spot. This fixes it."*). Looks at the hero PNG.
2. README "Installation" section gives them three commands: `/plugin marketplace add`, `/plugin install`, then **start a new session**, then `/found-issues:setup`. The "start a new session" call-out is *italic + bold* — good.
3. `/found-issues:setup` triggers the orientation prose and (assuming a `~/.claude/statusline.sh` exists and no `/fi` alias) a 2-option `AskUserQuestion` picker: *Statusline segment (Recommended)* + */fi short alias*.
4. User picks both. CLI runs `install-statusline` (auto-detects inline vs append, idempotent), then `install-fi-alias`. Setup prints `found-issues status --format=plain`, then touches `~/.claude/found-issues/.onboarded`.
5. They're done in ~30 seconds. The SessionStart hint is suppressed (marker file written).

### Friction observed

| # | Friction | Severity |
|---|---|---|
| 1.1 | **README and AGENTS.md disagree on install order.** README (line 30–34): "Then **start a new Claude Code session** … In the new session, run `/found-issues:setup`." AGENTS.md (line 11–16): "**Run all four commands.**" listing `marketplace add`, `install`, `/reload-plugins`, `/found-issues:setup` *in one shot, no restart*. Both can be made to work, but a fresh AI installing on the user's behalf reads AGENTS.md and chooses the four-command path; a fresh human user reads README. The two paths fork early. | P1 |
| 1.2 | **The "create `~/.claude/statusline.sh` first" fallback is a dead end for non-bash-experts.** `setup.md` line 116–117 tells the user: *"If you want a custom statusline with the counter inline, create `~/.claude/statusline.sh` first."* No template is provided. A non-bash operator has no idea what minimal contents to put there. They'll either bounce or paste a stale snippet from a blog post (precisely the kind of input that creates the legacy-snippet state v1.0.4 had to self-heal). | P2 |
| 1.3 | **Setup option 2 (per-repo pre-commit hook) is documented but unimplemented.** `setup.md` lines 137–149: *"(Available in a future release. For now, the in-Claude-Code format-enforcer hook handles this. Skip mentioning if it's not yet implemented.)"* This is instruction-to-self-that-leaks-into-the-spec. A fresh AI reading the doc may or may not skip it correctly. | nice-to-have |
| 1.4 | **First-run SessionStart hint relies on Claude obeying a prompt injection.** `hooks/session-start.sh` lines 28–37 emit *"Prepend this single italicized line to the very top of your next reply, then continue with whatever the user asked"*. This is a hard-to-test contract: if Claude is mid-deep-task or strict about formatting, it may skip the prepend. The user then misses the onboarding hint entirely and the marker is touched anyway, so the hint never fires again. | P2 |
| 1.5 | **The "Recommended" suffix carries the entire recommendation signal.** It's literally text — no color, no icon, no bold. Users who tab through `AskUserQuestion` pickers default-select the first option and may not parse "(Recommended)" as a strong cue. (This is a Claude Code platform limitation more than a plugin issue, but it's worth noting that the highest-signal integration ships behind a 12-character textual hint.) | nice-to-have |

### Recommended fixes

- **P1 — Fix the README/AGENTS.md divergence.** Pick one canonical install sequence and write the other to point to it. Recommendation: keep README's 2-command + restart + setup sequence (most predictable for humans), update AGENTS.md to match exactly, drop `/reload-plugins` from the AI path or document it as the *alternative* to a restart.
- **P2 — Ship a minimal-statusline-template subcommand.** `found-issues install-statusline --bootstrap` could write a 5-line `~/.claude/statusline.sh` with the canonical `LINE1` pattern + segment block, for users who don't already have one. Removes the "go figure out bash" cliff.
- **P2 — Remove the unimplemented per-repo-precommit prose from setup.md.** Either implement it or delete the section. As written, it's noise that asks the AI to silently skip a path.
- **nice-to-have — Replace the SessionStart "Prepend this italic line" directive with an actual stdout-rendered nudge.** Claude Code injects SessionStart stdout as system context; the user never sees it unless Claude paraphrases it. If the constraint is "no platform-rendered UI for SessionStart," then this is the best available — but it's worth periodically re-checking whether platform support has improved.

## Surface 2 — First-time statusline encounter

### Walked-through experience

User restarts CC. Their statusline now reads (assuming a brand-new repo, freshly logged one issue):

```
agent-config | main | 1 issue
```

Or with state accumulated:

```
agent-config | main | 2 critical · 5 issues · 1 in PR
```

### Friction observed

| # | Friction | Severity |
|---|---|---|
| 2.1 | **`issues` excludes `critical`. This is invisible.** `bin/found-issues:686`: `issues=$((total_open - in_pr - critical))`. A user reading `2 critical · 5 issues` will mentally sum to 7, but the actual `[open]` count is 7 *only because* critical is excluded from issues. Now think about `0 critical · 5 issues`: 5 total open. Compare to `2 critical · 5 issues`: also 7 total open, but the second number is *also* 5. Same "5 issues" means different total. Users will notice this mismatch when they ask Claude "what's open?" and the count seems off. | P1 |
| 2.2 | **No tooltip / no "what is this?" affordance.** A user with the segment sees `1 issue` and has zero entry points to learn more. The first time they ask Claude, Claude has the rules in context — but a self-discovery path through documentation requires them to already know the plugin's name. | P2 |
| 2.3 | **Hardcoded ` \| ` prefix may double-separate.** `bin/found-issues:736`: `printf ' \| %s' "$out"`. If the user's existing statusline already ends in ` \| `, they'll see `... main \| \|  3 issues`. The inline-install path inserts mid-LINE1 and joins with ` ` so this is mostly a problem for the append path. | nice-to-have |
| 2.4 | **Critical vs issues use the same red.** `bin/found-issues:722–723`: critical uses bold-red (`\033[1;31m`), issues uses plain-red (`\033[31m`). On many terminal themes the bold attribute reads as "slightly brighter" — not a clear priority signal. Yellow for in-PR + dim for stale are distinct enough. | nice-to-have |

### Recommended fixes

- **P1 — Reframe the counter math.** Either (a) include critical in issues and label `2 critical (of 7 issues) · …` (additive), or (b) keep critical/issues mutually exclusive but rename `issues` to `other` or `non-critical`. Recommendation: option (b), label as `2 critical · 5 other · 1 in PR`. "Other" is clearly the residual bucket and the total adds up.
- **P2 — Add a `found-issues explain` subcommand.** Single command that prints the four-counter rubric in plain English. README link the counter to it. Then "what does this mean?" → ask Claude → Claude runs `explain` → user gets a self-contained legend.
- **nice-to-have — Make critical visually distinct.** Use a different color (e.g. magenta or bold-orange) or wrap critical in a glyph (`!N critical`). Same red for two adjacent counters is a wasted signal.

## Surface 3 — First-time entry log

### Walked-through experience

Two paths:

**A. Claude logs it automatically.** Claude reads code, notices a defect, runs `/found-issues:log src/foo.py:42 — null check missing (suggested: add guard)`. Output: `Logged: - [open] 2026-05-10 src/foo.py:42 — null check missing (suggested: add guard)` + `1 issue`. The user sees this in Claude's reply (passed-through) and now has one tracked entry.

**B. User logs it manually.** User types `/fi log src/foo.py:42 — null check missing` themselves. Same flow; same output.

Subsequent identical observations dedup against the existing entry: `Skipped — already logged: <entry>`.

### Friction observed

| # | Friction | Severity |
|---|---|---|
| 3.1 | **Em-dash separator is a real footgun for manual users.** The CLI requires U+2014 (` — `). A user typing on a US keyboard cannot produce em-dash without OS-specific shortcuts (Mac: opt-shift-hyphen; Windows: Alt+0151). Hyphen (` - `) returns *"found-issues log: missing ' — ' separator"*. A first-time manual user will probably try `-` first, get the error, then either give up or paste from the README. Claude doesn't have this problem (it can output em-dash trivially); users do. | P2 |
| 3.2 | **The "user typically does NOT invoke this directly" framing in log.md is at odds with `/fi log` ergonomics.** `log.md` lines 26–28: *"The user typically does NOT invoke `/found-issues:log` directly. You invoke it on their behalf…"* But the README's "Want shorter typing?" section explicitly markets `/fi log` as a user-facing shortcut. Mixed signal: is this for the user or not? Both, but the doc tilts toward "agent only." | nice-to-have |
| 3.3 | **Skipped-because-deferred is invisible to stdout consumers.** `cmd_log` (`bin/found-issues:357–360`) branches into `fi_handle_deferred_touch` when the dedup hits a `[deferred]` entry. That function prints all feedback on stderr (lines 196, 206–207, 212). Claude Code passes stderr through to Claude's context, but if a wrapper (e.g. a `/fi` user-typed call via a different harness) doesn't surface stderr, the user types `/fi log <thing>` and sees no output at all — entry was silently touched, no acknowledgement. | P1 |
| 3.4 | **Dedup is symptom-exact, not symptom-similar.** Two slightly different phrasings of the same issue both get logged. `bin/found-issues:295` builds the key from `fi_dedup_key_abstract "$symptom"` (whole symptom string). The README roadmap mentions "AI-assisted dedup for semantic-similar entries" as a future. Not a fix for v1.0.6, but worth being honest in the docs: dedup is literal. | nice-to-have |

### Recommended fixes

- **P1 — Make `fi_handle_deferred_touch` print to stdout, not just stderr.** Or print a single stdout summary line (e.g. `Touched deferred entry (1x of 3): src/foo.py:42`) in addition to stderr. Stderr-only feedback is invisible to many wrapping contexts.
- **P2 — Accept hyphen as separator in the CLI, normalize to em-dash on write.** The format-enforcer hook already validates the *file*. Letting the CLI accept either separator on input would remove the footgun without changing the canonical format. Document the canonicalization in `--help`.
- **nice-to-have — Soften the framing in log.md.** *"This is the primary way agents log entries; users can invoke it directly via `/fi log` for ad-hoc cases."* Removes the "this isn't for you" tone for the small audience that types it manually.

## Surface 4 — defer + recurrence flow (NEW v1.0.5)

### Walked-through experience

1. User (or Claude) decides an entry is real-but-deferrable. They run `/found-issues:defer src/auth.py --reason "blocked on AUTH-1234"`.
2. CLI flips `[open]` → `[deferred]`, adds `(reason: blocked on AUTH-1234)`. Output: `Deferred 1 entry. (cycle 1, threshold for nudge: 3 touches)`.
3. The entry no longer counts toward `issues` in the statusline.
4. On subsequent log attempts that match this entry's dedup key, the entry's `(touched: ...)` annotation gets today's date appended. After 3 touches in cycle 1, stderr emits *"Touched deferred entry (now 3x, threshold 3): src/auth.py"* + *"Consider: found-issues promote-deferred --match auth.py"*.
5. If the entry was `[!]` critical, it auto-promotes on touch 3 instead of nudging.
6. User runs `/found-issues:promote-deferred src/auth.py`. Entry flips back to `[open]` with all annotations preserved (touch history, defer-cycle, reason).
7. If the user defers again, `(defer-cycle: 2)` is added and threshold becomes 6 for the next nudge.

### Friction observed

| # | Friction | Severity |
|---|---|---|
| 4.1 | **`--reason` overwrites prior reasons silently.** `cmd_defer` line 509: `new_line="$(printf '%s' "$new_line" \| sed -E 's/ \(reason: [^)]+\)//g')"`. Strips the existing reason before appending the new one. The defer message reports `(cycle 2, threshold for next nudge: 6 touches)` but says nothing about *"replaced prior reason 'blocked on AUTH-1234' with 'now blocked on legal review'"*. Defer-cycle 3+ users lose their context trail unless they read the file directly. | P2 |
| 4.2 | **Threshold-progress nudge is below-threshold-only.** `fi_handle_deferred_touch` line 195: `if (( count < threshold )); then printf 'Touched deferred entry (%dx of %d for promotion)'`. At count == threshold, the nudge ("now Nx, threshold N") fires. Above threshold (e.g. user ignores the nudge and the entry gets touched a 4th time in cycle 1), the loop falls through both branches — no message printed at all. Silent on overshoot. | P1 (mild) |
| 4.3 | **Nudge is stderr-only; same problem as 3.3.** A user-driven `/fi log` that hits a deferred entry on a wrapper that swallows stderr sees nothing. | (covered by 3.3) |
| 4.4 | **Threshold default of 3 is aggressive for genuinely-deferred items.** If the user defers because "this is blocked on legal" and 3 unrelated touches happen over a week (e.g. Claude grep-finds the same file by accident during unrelated work), the nudge fires. The user doesn't want the nudge — the entry is *still* blocked on legal. The geometric escalation (3 → 6 → 12) does eventually quiet the nudge, but only after re-defers, which is busywork. | P2 |
| 4.5 | **`defer-cycle: 1` is implicit (no annotation).** First-cycle entries have no `(defer-cycle: 1)` token; second-cycle entries gain `(defer-cycle: 2)`. A reader of the file can't tell "no annotation" from "cycle 1" except by absence. Minor but matters for grep-based queries. | nice-to-have |
| 4.6 | **Annotation order is non-deterministic after re-defer.** `cmd_defer`'s "strip existing reason then append new reason" path puts the new `(reason: ...)` at the end of the line. But `fi_increment_defer_cycle` (lib/parse-entries.sh:415) appends `(defer-cycle: N)` separately. Over 3+ cycles the order could become `… (touched: ...) (defer-cycle: 3) (reason: X) (touched: ...) (PR: ...)` — readable but inconsistent across entries. | nice-to-have |

### Recommended fixes

- **P1 — Make the nudge also fire on overshoot (count > threshold).** Print the same "Consider: found-issues promote-deferred" line. If the user is ignoring the nudge intentionally, they can re-defer. If they're ignoring because they missed it (stderr swallowed somewhere), they get re-reminded.
- **P2 — Preserve prior `(reason: ...)` annotations on re-defer.** Either append a new `(reason: ...)` (multi-reason allowed; mirrors how multi-PR works) or migrate to `(reasons: "old"; "new")` cycle-separated. Recommendation: allow multiple `(reason: ...)` and append, mirroring PR/commit semantics.
- **P2 — Add a per-defer `--mute-until <date>` flag.** Hard-suppresses the nudge until a date. Solves the "blocked on legal review for 6 weeks" case without forcing re-defers as a workaround.
- **nice-to-have — Always write `(defer-cycle: N)` even when N == 1.** Removes the implicit-default footgun for grep consumers and external tooling.

## Surface 5 — Sync + closure flows

### Walked-through experience

1. **Automatic (SessionStart).** Every session start, the hook runs `found-issues sync >/dev/null 2>&1 || true`. PR-merge + commit-on-default + tombstone closures all flip silently. The user sees no output — they just notice the counter dropped on a new session.
2. **Manual.** User runs `/found-issues:sync`. CLI phase 1 prints `Synced. Closed: N (P PR + C commit + T tombstone).` Then phase 2 (AI verification) — Claude reads each unannotated `[open]` entry's `path:line`, judges still-present / fixed / unclear, conservatively flips only the clear-cut "fixed" cases.
3. Auto-archive runs after sync (`bin/found-issues:1074`). Old `[fixed]` entries move to `docs/found-issues-archive.md`.

### Friction observed

| # | Friction | Severity |
|---|---|---|
| 5.1 | **Phase 2 has no rate limit.** `commands/sync.md` instructs Claude to Read every unannotated `[open]` entry's location. On a 100-entry queue that's 100 Read invocations + 100 judgments — easily 30K+ tokens of context for entries that mostly will judge "unclear" anyway. The conservative bias is correct, but the work envelope is unbounded. A `--max-verifications=N` knob would let the user say "verify the 10 oldest unannotated entries this round." | P2 |
| 5.2 | **The SessionStart silent sync masks real errors.** `hooks/session-start.sh:146`: `"$FI_BIN" sync >/dev/null 2>&1 \|\| true`. If sync starts failing (e.g. `gh` auth expired, network down, repo cache corruption), the user sees a counter that's slowly drifting from reality and has no signal that anything's wrong. A daily-or-on-state-change sanity check (`found-issues doctor`) doesn't exist. | P2 |
| 5.3 | **PR-merge check on a non-default-branch merge is silently a no-op.** `cmd_sync` line 996: `if [[ "$pr_state" == "MERGED" && ( -z "$default_branch" \|\| "$pr_branch" == "$default_branch" ) ]]`. A PR merged into a release branch (or a feature integration branch) won't flip the entry. Probably correct behavior for most projects, but for monorepos with non-`main` integration the entry stays `[open]` forever. No diagnostic. | nice-to-have |
| 5.4 | **No "summary of what changed since last session" surface.** SessionStart hook injects the list of currently-open entries. It does *not* surface "1 entry flipped to [fixed] during silent sync this session" — so the user never sees the closure feedback loop. They only see counts go down. | nice-to-have |

### Recommended fixes

- **P2 — Add `found-issues sync --quiet=closures-only`** that prints a one-liner when sync actually closed something. Use that in the SessionStart hook so closures are surfaced (additive, never blocks).
- **P2 — Add `found-issues doctor` (general-purpose).** Wraps `doctor-statusline` plus: gh auth state, mode-cache integrity, last sync timestamp, suspicious entry counts (e.g. `[open]` with `(fixed: ...)`, `[fixed]` without it). One command, full diagnosis, no edits.
- **P2 — Cap phase 2 in sync.md prose: "Verify at most 10 entries per sync invocation."** With a re-run hint. Prevents context blowups on neglected repos.
- **nice-to-have — Document the non-default-branch PR-merge edge case in `docs/modes.md`.**

## Surface 6 — Uninstall flow (CRITICAL)

### Walked-through experience

1. **Canonical path (per README "Uninstalling" section).** User runs `/found-issues:uninstall` first, then `/plugin uninstall found-issues`, optionally `/plugin marketplace remove altdoug-plugins`. Plugin-private state in `~/.claude/` and `~/.cache/` gets cleaned before the plugin code disappears.
2. **Most-likely actual path.** User remembers the platform pattern from other plugins and runs `/plugin uninstall found-issues` first. CLI vanishes from PATH. The skill `/found-issues:uninstall` is also gone. `~/.claude/found-issues/`, `~/.cache/found-issues/`, `~/.claude/statusline.sh`'s marker block, and `~/.claude/commands/fi.md` all survive as orphans. Reinstall later → state mismatches → silent breakage.

### Friction observed

| # | Friction | Severity |
|---|---|---|
| 6.1 | **AGENTS.md tells AIs to use the wrong uninstall path.** AGENTS.md lines 102–112: *"Users uninstall via: `/plugin uninstall found-issues`. This removes hooks from their settings, removes the CLI from PATH, and deletes the plugin's data directory."* That's directly wrong — `/plugin uninstall` does **not** delete `~/.claude/found-issues/`, the statusline block, the mode cache, or the `/fi` alias. README is correct; AGENTS.md is stale. An AI helping with uninstall will follow AGENTS.md and create exactly the orphan state PR #50 was meant to mitigate. | **P1** |
| 6.2 | **No pre-uninstall safety hook (platform limitation).** README acknowledges this — the only mitigation is README prominence + `/found-issues:uninstall` discoverability. Mitigation through docs is the right move given the platform constraint, but the surface remains fragile until Claude Code adds a `PreUninstall` hook. | nice-to-have (architectural; tracked as deferred entry already) |
| 6.3 | **Orphan-state detection only fires on the statusline.** SessionStart self-heal nudge looks for broken statusline state and nudges. It does *not* check for orphaned `~/.claude/found-issues/`, orphaned mode cache, or orphaned `/fi` alias. If the user reinstalls after a wrong-order uninstall, those orphans persist invisibly. | P2 |

### Recommended fixes

- **P1 — Fix AGENTS.md to match README.** Rewrite the "Uninstalling" section to require `/found-issues:uninstall` first. AGENTS.md is the document an AI assistant reads when *acting on a user's behalf* — it can't disagree with the README. Add a regression test (just a grep) that fails CI if AGENTS.md and README's uninstall sections drift apart on the ordering keyword.
- **P2 — Extend the SessionStart self-heal nudge to cover all orphan types.** If `~/.claude/found-issues/` or `~/.cache/found-issues/` exists but the plugin isn't installed (CLI not on PATH and plugin dir absent), emit a one-line "stale found-issues state detected — `rm -rf ~/.claude/found-issues ~/.cache/found-issues` to clean" nudge. Same once-per-day pattern.
- **nice-to-have — Add `found-issues doctor` checks for orphan state.** (covered under 5.2 fix.)

## Surface 7 — Per-repo dogfood file (`docs/found-issues.md`)

### Walked-through experience

User opens `docs/found-issues.md` in their editor. Sees:

```
- [fixed] 2026-05-09 .github/workflows/test.yml — no CI guard against non-ASCII test names; ... (PR: AltDoug/found-issues#40) (fixed: 2026-05-10)
- [deferred] 2026-05-10 bin/found-issues:1166 cmd_install_statusline — has no awareness of whether ~/.claude/statusline.sh is the canonical machine file ... (reason: wait for second user report per entry guidance)
```

Active entries are scannable. With 5–10 entries, the format is human-friendly.

### Friction observed

| # | Friction | Severity |
|---|---|---|
| 7.1 | **Annotation soup will become unwieldy after 2–3 defer cycles.** The README example (lines 116–125) shows `(touched: 2026-05-08, 2026-05-09; 2026-05-10) (defer-cycle: 2) (reason: ...)`. Add a multi-PR entry and you can hit 400+ characters per line. Editors that wrap visually mask the structure; editors that don't, scroll horizontally. There's no "compact view" — every annotation is always visible. | P2 |
| 7.2 | **Symptoms are arbitrarily long.** Dogfood line 11 has a 1300-character symptom + suggested fix combined. Useful as evidence; brutal as a single line. Markdown doesn't render this as anything but a long bullet. | P2 |
| 7.3 | **Archive threshold (count=50 OR days=30) is invisible until it fires.** No `found-issues status` surfaces "you're at 47 of 50, archive will fire on next sync." Users get surprised when their `[fixed]` history suddenly migrates to a sibling file they didn't know existed. | nice-to-have |

### Recommended fixes

- **P2 — Add `found-issues fmt --compact` mode.** Rewrites the active file with annotations folded into a trailing reference id, full text in a "trailer block" at the bottom of the file. Optional, reversible. Keeps the grep-friendly structure but improves human scan-ability.
- **P2 — Soft-wrap symptom + suggested fix at write time.** When the CLI logs an entry, if the symptom exceeds N chars, truncate to N with `…(see <ref>)` and stash the full text in an entry-keyed trailer comment block. Or: don't truncate, but document the 80–120 char target in `docs/format-spec.md`.
- **nice-to-have — Surface archive-pending count in `status --format=plain` when within 10% of threshold.**

## Surface 8 — Hooks ergonomics

### Walked-through experience

7 hooks register via `hooks.json`:

- `PreToolUse`: `format-enforcer.sh` (Write/Edit/MultiEdit), `pre-branch-delete.sh` (Bash)
- `PostToolUse`: `post-pr-create.sh`, `post-git-commit.sh` (both Bash)
- `SessionStart`: `session-start.sh`
- `Stop`: `stop-reminder.sh`
- (+ `pre-commit.sh` — opt-in per-repo git hook, not in `hooks.json`)

Most hooks fail-open. The Stop hook is the only one that hard-blocks on tool-substantive turns.

### Friction observed

| # | Friction | Severity |
|---|---|---|
| 8.1 | **`pre-branch-delete.sh` false-positives on merged-via-PR branches.** `hooks/pre-branch-delete.sh:110`: `if [[ -z "$main_content" ]] \|\| ! printf '%s' "$main_content" \| grep -Fxq -- "$line"; then`. This is **full-line equality** between the branch's `docs/found-issues.md` entry and main's. Scenario: branch logs `[open] … src/foo:42 — bug`. Branch annotates `(PR: org/repo#5)`. PR merges. Main sync flips to `[fixed] … src/foo:42 — bug (PR: org/repo#5) (fixed: 2026-05-10)`. Branch's original `[open]` line *does not match* main's new `[fixed]` line — equality fails — hook blocks deletion. This is the surprise the handoff calls out from today's `fix/install-statusline-cwd` cleanup. **Real bug, not over-protection by design.** | **P0** |
| 8.2 | **`FOUND_ISSUES_STOP_REMINDER=off` is hidden.** The opt-out exists in the hook source (`stop-reminder.sh:17`) and is mentioned in the rules SKILL.md but is not surfaced in README, setup.md, or `--help`. A new user who finds the marker-requirement annoying has no documented escape hatch short of reading the source. | P1 |
| 8.3 | **Stop hook smart-fire heuristic looks for tool names by string match in the last 16KB of transcript.** `hooks/stop-reminder.sh:60`: `grep -qE '"name":"(Edit\|Write\|MultiEdit\|Bash\|NotebookEdit)"'`. A 16KB tail may straddle a user message boundary mid-tool-call, or — on long agent turns — exclude the actual tool use entirely (16KB is small for verbose Bash). False positives (no marker needed when there should be one) and false negatives (marker required for a pure-conversation turn) are both possible. | P2 |
| 8.4 | **Format-enforcer fires `PreToolUse` on every Write/Edit/MultiEdit, even for unrelated files.** The early-exit (`format-enforcer.sh:47–50`) is fast (case statement on file_path), but the hook is invoked. Cumulative cost on a heavy edit session is non-zero. Minor. | nice-to-have |
| 8.5 | **`post-pr-create.sh` and `post-git-commit.sh` both run on every Bash PostToolUse.** Each one parses JSON + greps the command. Two independent JQ invocations per Bash call. Combining them into one router script would halve the overhead. Not urgent. | nice-to-have |
| 8.6 | **`FOUND_ISSUES_PROMOTE_GUARD=off` (pre-branch-delete opt-out) is also hidden.** Same shape as 8.2. | P2 |

### Recommended fixes

- **P0 — Fix `pre-branch-delete` matching to use dedup keys, not full-line equality.** Parse each branch-only `[open]` entry via `fi_parse_entry`, build its dedup key (path:line:symptom), then check whether any entry in main (regardless of status) has the same key. If yes, the entry was promoted — allow delete. If no, block. Mirror this with a regression test based on today's actual breakage shape (branch [open] + main [fixed] with annotations).
- **P1 — Document the opt-outs.** Add a "Hook opt-outs" section to README (or a dedicated `docs/hooks.md`). List `FOUND_ISSUES_STOP_REMINDER`, `FOUND_ISSUES_PROMOTE_GUARD`, `FOUND_ISSUES_FORMAT_ENFORCER`, `FOUND_ISSUES_PRE_COMMIT`, `FOUND_ISSUES_AUTO_ARCHIVE`. Concrete examples. Cross-link from `commands/setup.md` so a user who just installed knows their escape hatches.
- **P2 — Improve the Stop-hook smart-fire heuristic.** Track substantive-tool-use as a transcript-level marker (write to a session-scoped state file when a tool fires) rather than parsing transcript bytes. Or expand the tail window to 32KB. Test against a 5-tool-use long-output turn.
- **nice-to-have — Merge post-pr-create + post-git-commit into a single router script.** Trivial perf win; cleaner mental model.

## Cross-cutting observations

A few patterns surfaced across multiple surfaces:

1. **Stderr is doing too much load-bearing work.** Three findings (3.3, 4.2, 4.3) hinge on user-visible feedback being sent to stderr only. Stderr is reliably surfaced *to Claude* in tool results but is much less reliable for *user-facing wrappers* (statusline tools, IDE integrations, future Codex/Cursor adapters). For any feedback the user is meant to act on, stdout is the safer channel.
2. **AGENTS.md is drifting from README.** Two divergences in this audit (install order, uninstall order). AGENTS.md is the AI-facing source of truth; the README is the human-facing source of truth. They must agree on the operational sequence. Add a doc-consistency CI check.
3. **Env-var opt-outs exist but are scattered.** At least 5 plugin behaviors have env-var opt-outs (`STOP_REMINDER`, `PROMOTE_GUARD`, `FORMAT_ENFORCER`, `PRE_COMMIT`, `AUTO_ARCHIVE`) + 2 tunables (`DEFER_TOUCH_THRESHOLD`, `DEFER_ESCALATION_FACTOR`, `STALE_DAYS`). None are listed in README. A `docs/configuration.md` or README "Configuration" section would solve all of 8.2/8.6/9.2 at once.
4. **The "fix the statusline self-heal" arc is at v3.** v1.0.2 → v1.0.3 → v1.0.4 each shipped a tighter migration story. v1.0.4 is in a good place. Worth pausing iteration here unless the deferred external-sync-layer issue surfaces a new failure mode.
